# QR Simple — Agent Notes

QR-based quick-info lookup for mining equipment. Domain vocabulary lives in [CONTEXT.md](CONTEXT.md) — read it before touching Equipment/Organization/Role terminology. Architectural decisions with real trade-offs are recorded in [docs/adr/](docs/adr/); check there before "fixing" something that looks wrong (e.g. why a QR code is never regenerated).

The full spec — every user story, in and out of scope for v1 — is [GitHub issue #1](https://github.com/tsogtbatjargal/qr-simple/issues/1). This file does not restate it; it tracks what's built versus what's left.

Setting up a dev environment from scratch (new machine, or a devcontainer rebuild that wiped host-side state)? [docs/getting-started.md](docs/getting-started.md) is the ordered checklist — this file assumes that's already done.

Picking up a piece of work that was planned out in a separate session before being handed to you? Check [docs/plans/](docs/plans/) first — [docs/plans/README.md](docs/plans/README.md) explains the workflow, and each numbered plan there is a scoped implementation spec (decisions, design sketch, verification checklist) with its own Log section for what actually happened. Append to that Log as you work; don't just report back in chat and let the trail disappear.

**If a handoff describes uncommitted changes but `git status` shows a clean tree, `git fetch origin` before concluding the work doesn't exist.** Multiple agents/sessions (Codex and Claude Code, devcontainer and bare-host) work this repo in parallel and hand work between each other via out-of-band prompts, and a session's local clone doesn't automatically know about a branch another session pushed. Real incident, 2026-08-28: a rebrand handoff described 23 modified files sitting uncommitted in the working tree; `main` was actually clean, and the real work — committed, matching the description exactly — was sitting on `origin/rebrand/ics-brand-tokens`, a branch that simply hadn't been fetched yet. Don't spend time concluding a briefing is "stale" or "for a different repo" before ruling this out with a fetch.

## Architecture

ASP.NET Core minimal API (`src/QrSimple.Api`) + PostgreSQL via EF Core, tested at a single seam: real HTTP requests in-process (`WebApplicationFactory<Program>`) against a real containerized Postgres (Testcontainers) — no mocking, no unit tests below that seam. `tests/QrSimple.Api.Tests/ApiFactory.cs` is the fixture; every test class implements `IClassFixture<ApiFactory>`.

`Program.cs` is a thin HTTP adapter — routes translate requests into calls on these modules and translate results back into responses. It should stay thin; if you find yourself adding a validation rule or business decision directly inside a route lambda, that logic belongs in one of the modules below instead:

- **`EquipmentCatalog`** — single-Equipment lifecycle (create, update, retire, reactivate). Owns category validation and the Admin-vs-Operator field-edit split: `UpdateAsync` takes the caller's role and rejects (`RestrictedFieldEdit`) an Operator's attempt to change `Name`/`SerialNumber` — Operators may only change `Category`/`Site`; Admins may change everything. Retiring/reactivating (status changes) are Admin-only at the route level (`RequireRoleFilter(Roles.Admin)`), not inside this module, since there's no partial-permission case to express there. This role split applies only to the `PUT /equipment/{id}` route and its Blazor UI (`EquipmentDetail.razor`) — the CSV bulk-import "update existing" path (`EquipmentImport.cs`) intentionally does its own unrestricted field overwrite and was left out of this restriction as a deliberate scope decision, not an oversight. Returns an `EquipmentResult` (`Success` / `NotFound` / `UnknownCategory` / `RestrictedFieldEdit`); call `.ToHttpResult(onSuccess)` to turn it into a response — don't hand-write a new `switch` per route, `NotFound`/`UnknownCategory`/`RestrictedFieldEdit` already map correctly for every case.
- **`Equipment.Create(...)`** — the one place that constructs a new Equipment (`Id = Guid.NewGuid()` + field mapping). Both `EquipmentCatalog` and `EquipmentImport` call it — add a new required field once, here, not at every construction site.
- **`EquipmentImport`** — bulk CSV import: parsing, duplicate skip+report, update-existing upsert mode.
- **`RequireRoleFilter`** — an `IEndpointFilter` gating write endpoints by role. Applied per-route via `.AddEndpointFilter(new RequireRoleFilter("Admin", "Operator"))`.
- **`UserCatalog`** — single-User lifecycle (create, update role, deactivate/reactivate). Owns duplicate-email, unknown-role, last-admin-protection, and self-lockout-protection checks. Returns a `UserResult` (`Success` / `NotFound` / `UnknownRole` / `DuplicateEmail` / `LastAdminProtected` / `SelfLockoutBlocked`); call `.ToHttpResult(onSuccess)` the same way as `EquipmentResult` above.
- **`Roles`** — centralizes the three role constants (`Admin`, `Operator`, `Reader`) plus `IsKnown(role)`. Don't compare against role string literals elsewhere.
- **`CategoryCatalog`** — single-Category lifecycle: create, rename, delete. Owns duplicate-name rejection. Returns a `CategoryResult` (`Success` / `DuplicateName` / `NotFound` / `InUse`); call `.ToHttpResult(onSuccess)` the same way as `EquipmentResult`/`UserResult` above. No DB-level unique index on `Category.Name` (unlike `User.Email`) — `Equipment.Category` is a plain string, not a foreign key, so a duplicate name can't cause a crash the way the duplicate-email bug did; the app-level check alone is enough to keep the UI from producing confusing duplicate dropdown entries. Because `Equipment.Category` is a free-text copy rather than a foreign key, `RenameAsync` and `DeleteAsync` handle the two destructive cases asymmetrically **on purpose**: rename cascades (bulk-updates every matching `Equipment.Category` row inside the same DB transaction as the `Category.Name` update, via `ExecuteUpdateAsync` + `SaveChangesAsync` sharing one `BeginTransactionAsync()`), while delete is blocked outright (`InUse`) whenever any equipment still references the name — there's no sensible name to fall back equipment onto, so silently clearing the field would leave equipment with an invalid category in its own edit dropdown. If you're tempted to "fix" delete to cascade too (e.g. null out or blank the field), don't — that's the deliberate choice, not a gap. `InUse`'s count includes retired equipment on purpose (retiring something shouldn't silently erase its category history) — `Components/Pages/EquipmentList.razor` has a "Show retired" checkbox (loads once via `ListAsync(includeRetired: true, db)`, filtered client-side) specifically so an admin blocked by an `InUse` count they can't otherwise explain can actually go find the equipment behind it; don't remove that toggle or default it back to active-only without keeping some other way to reconcile that count.
- **`DocumentCatalog`** — `Document` (equipment photo + doc links) lifecycle, upload-based as of 2026-08-17 (see `docs/plans/0001-document-file-upload.md`): `Document` has `Content: byte[]?`/`ContentType: string?`/`FileName: string?` (the bytes, stored directly in Postgres) plus a `Url: string?` kept nullable in the model for a possible future link-only mode — nothing in the app sets `Url` today, only `Content`. `AddUploadAsync(equipmentId, label, content, contentType, fileName, db)` (generic upload, used by both the public `POST /equipment/{id}/documents` endpoint and the admin "Add document" form; `label` is optional — if null/blank, it's derived from the filename) and `SetPhotoUploadAsync(equipmentId, content, contentType, fileName, db)` (photo-specific: overwrites the existing photo row's `Content`/`ContentType`/`FileName` in place if one exists, instead of inserting a second one) both validate the file first via `DocumentUpload.Validate(fileName, contentType, sizeBytes, isPhoto)` — extension + browser-reported `ContentType` only, no magic-byte sniffing (internal tool, trusted Admin/Operator roles) — returning `DocumentResult.InvalidFile(reason)` (mapped to 400) on rejection. Photos: `.jpg`/`.jpeg`/`.png`/`.webp`, 5MB cap. Documents: `.pdf`/`.doc`/`.docx`/`.xls`/`.xlsx`, 20MB cap. **The single-photo invariant is enforced only by `SetPhotoUploadAsync`, not at the DB or `AddUploadAsync` level** — same shape as before the upload rework, just renamed. `ScanPage.Render` picks the header photo via `documents.FirstOrDefault(d => label is "Equipment Photo" or "Equipment Image")` — if two photo-labeled documents ever exist for the same equipment, which one "wins" depends on undefined DB row order. `AddUploadAsync`/the public POST endpoint intentionally still allow any label including the reserved photo ones, so it's `EquipmentDetail.razor`'s admin UI, not the catalog, that blocks a user from creating a duplicate photo through the generic "Add document" picker (checks `DocumentCatalog.IsPhotoLabel(...)` against the filename-derived label before calling `AddUploadAsync`) and instead routes them to the dedicated Photo section, which always goes through `SetPhotoUploadAsync`. If you add another caller that creates documents (import, seed script, another endpoint), it will NOT get this protection for free. **There is no HTTP route for setting the photo** — `SetPhotoUploadAsync` is only called in-process by `EquipmentDetail.razor`'s Photo section (see the `Components/` bullet below on why Blazor pages call these modules directly rather than through HTTP); a test or external caller that needs to seed a photo document must call `SetPhotoUploadAsync` directly via a scoped `AppDbContext` (`factory.Services.CreateScope()`, see `DocumentUploadTests.cs`), not the generic POST endpoint — that endpoint validates against the *document* extension set, so a `.png` upload through it is always rejected with 400. `GET /documents/{id}/content` (no auth, no role filter — the public `/e/{id}` scan page needs to load photos/docs without a login, matching the exposure the old `Url`-based design already had) streams the stored bytes with the stored `ContentType`; it 404s if the document doesn't exist or has no `Content` (i.e. it's a future URL-based row). **Anywhere a `Document` is rendered must branch on `Content is not null` vs `Url` (see `ScanPage.Render`'s `equipmentImage`/document-link `switch` and `EquipmentDetail.razor`'s `DocumentHref(document)` helper) rather than unconditionally linking to `/documents/{id}/content`.** This bit for real, not just hypothetically: the shared dev database already had `Documents` rows from before the 2026-08-17 upload migration with `Url` set and `Content` null (the migration only added nullable columns, it didn't touch existing rows), so an unconditional `/documents/{id}/content` link 404s for every one of them. If you add a new place that renders a `Document`'s link/image, copy the branch, don't assume every row has been uploaded through the new path. `Document.EquipmentId` has no DB-level foreign key or index (see the `Documents` table migration) — nothing cascades if `Equipment` rows are ever hard-deleted; there is no hard-delete for `Equipment` today (only retire), so this hasn't mattered yet, but would need handling if that changes.
- **`InspectionCatalog`** — `Inspection` (periodic-check PDF) lifecycle: `AddAsync`, `EditAsync`, `ListAsync`, `CountAsync`, `GetContentAsync`, `DeleteAsync`, plus the pure `SplitByRecency` helper the public inspections page uses to split the last-6-months/older view (see `docs/plans/0002-inspection-records.md` decisions 16-17). Unlike `Document`, `Inspection.Content`/`ContentType`/`FileName` are non-nullable — there are no legacy rows and no URL-link mode for this entity, so every render/read site can assume bytes exist and skip the `Content`-vs-`Url` branch `Document` requires everywhere (decision 2). **`ListAsync` projects `Content` away** into `InspectionListItem` — it's the one place the "bytes live in Postgres" decision actually bites, since listing 50 inspections to render a page that displays none of the bytes would otherwise pull 50 PDFs into memory; `GetContentAsync` is the only path that loads `Content`. `GET /e/{id}/inspections` and `GET /inspections/{id}/content` are public by design, no auth and no role filter, matching `GET /documents/{id}/content` (decision 10) — but `UploadedByEmail` is stored on every row and rendered only in the admin UI (`EquipmentInspections.razor`), never on the public page (decision 11); if you add a new public rendering of an `Inspection`, do not let that field leak into it. Deleting is Admin-only (`DELETE /equipment/{id}/inspections/{inspectionId}`), unlike Document delete which is Admin+Operator — an Operator hard-deleting their own filed inspection would defeat the provenance the `UploadedByEmail`/`UploadedAtUtc`/`LastEditedAtUtc`/`LastEditedByEmail` fields exist to preserve (decision 12); Operators may still correct `Note`/`InspectionDate` on records they uploaded via `PUT /inspections/{id}` (decision 13), never the PDF itself. **`GET /inspections/{id}/content` sets `Content-Disposition: inline` manually** (`ContentDisposition.BuildInlineHeader`) rather than passing `fileDownloadName` to `Results.File` — that forces `attachment` and stops phones displaying the PDF inline; the generated filename pairs an ASCII-sanitised `filename` with an RFC 5987 `filename*` since Equipment names may contain Cyrillic (decision 19).
- **`QrCode`** / **`ScanPage`** — QR PNG generation and the public scan-page HTML, respectively.
- **`GlobalExceptionHandler`** (`IExceptionHandler`, wired via `AddExceptionHandler<T>()` + `app.UseExceptionHandler()`) — catches anything unhandled app-wide, logs the full exception server-side, and returns a generic JSON 500 with no exception detail to the client. Typed, expected errors (`UnknownRole`, `DuplicateEmail`, etc. above) never reach this — they're already turned into proper 400/404/409 responses by `.ToHttpResult()` before an exception would occur. Live-verified 2026-08-15: a malformed CSV to `/equipment/import` throws `CsvHelper.HeaderValidationException` before any `SaveChangesAsync`, so nothing is half-written, and the client only ever sees the generic message.
- **`Components/`** — the Blazor Server admin UI (sign-in, Equipment list/add/detail, `/app/categories` list/add/detail, and `/app/users` list/add/detail, all Admin/Operator/Reader-gated). Pages call the modules above in-process (`EquipmentCatalog`, `UserCatalog`, `CategoryCatalog`, `QrCode`) rather than the JSON HTTP endpoints — they're another thin adapter, not a client of the API. Use `IDbContextFactory<AppDbContext>` here, not `AppDbContext` directly — a Blazor Server circuit's DI scope outlives a single request. `RoleGatedComponentBase` and `MainLayout.razor`'s nav-link check both gate on `user.IsActive` in addition to `user.Role` — a deactivated user's already-open Blazor session loses admin pages/nav immediately, matching what the API endpoints already enforced via `UserAuthorization.RequireRole`. It also injects a shared `ToastService` (see `Components/Shared/ToastHost.razor`, mounted once in `MainLayout`) so any page can call `Toast.Success(...)`/`Toast.Error(...)` without wiring its own notification UI.
- **Blazor/Razor gotchas that will bite you again if you're not looking for them** (all hit and fixed live while building the confirm-dialog/toast/sort/validation features — see `Components/Shared/ConfirmDialog.razor`, `EquipmentList.razor`, `wwwroot/app.css`):
  - **Mutating a `@ref`-captured child component's field from the parent's event handler does not make that child re-render.** Blazor's diff pass skips a child component subtree whose *parameters* haven't changed — it doesn't know or care that you poked a private field on the instance directly. `ConfirmDialog.Show()` learned this the hard way: the parent's `@onclick="() => SomeDialog!.Show()"` correctly flipped `Visible = true` on the child, but nothing rendered until `Show()` itself called `StateHasChanged()` on that component. Any future `@ref`-driven "imperative" child (modal, popover, toast-like widget) needs the same self-`StateHasChanged()` inside every method that mutates its own render-affecting state from outside.
  - **`word@Expression(...)` with no whitespace between the preceding text and `@` silently renders as literal text, not code.** Razor has a built-in heuristic that treats `foo@bar` as prose (an email address) rather than a code transition, specifically so you don't have to escape `@` in sentences like "contact us at foo@bar.com". `<th>Category@SortArrow("Category")</th>` rendered the literal string `@SortArrow("Category")` on the page for exactly this reason — no compile error, no runtime error, just wrong output. Fix: use explicit expression syntax, `@(SortArrow("Category"))`, or add a space. Suspect this immediately if a Razor expression renders as literal text with zero exceptions anywhere.
  - **A CSS class-selector override can lose to a more specific base rule even when it appears later in the file.** `app.css`'s base input rule is `input:not([type=submit]):not([type=checkbox]):not([type=radio])`, whose three `:not([...])` arguments each count toward specificity — that beats a plain `input.invalid` selector despite source order, so the border silently never turned red even though Blazor's automatic `modified invalid` CSS classes (see below) were genuinely present on the element. Any override targeting that base input rule needs matching or higher specificity (repeat the `:not()` chain, as the current `.invalid` rule does) rather than assuming "later in the file wins."
  - **Blazor's `InputText`/`InputSelect` automatically grow `modified`/`valid`/`invalid` CSS classes based on `EditContext` field state — you don't add them yourself.** Per-field validation already runs on blur (not just on submit) because `<InputText @bind-Value="...">` binds via `onchange`, and `DataAnnotationsValidator` subscribes to `EditContext.OnFieldChanged` and revalidates just that field. So "live" as-you-type-adjacent validation feedback is CSS + a `<ValidationMessage For="...">` per field, not custom JS or extra event wiring — don't build a debounced input handler for this, it already exists.
  - **When live-testing an `@bind-Value` (`onchange`) input with Playwright, clicking submit right after `browser_type`/`.fill()` can submit before Blazor Server's SignalR round-trip has updated the bound field, producing a spurious `[Required]` validation error even though the DOM clearly shows the typed value.** Hit this building the equipment Photo/Document forms: `Save photo` failed with "The Url field is required." on the first click, and again on an immediate retry, purely because the `change` event's server round-trip hadn't completed yet — not an app bug. Fix for live testing: add a short `browser_evaluate` delay (a few hundred ms) between typing and clicking submit, or dispatch `input`+`change` via `browser_evaluate` yourself and wait before submitting. Don't mistake this for a real validation bug without first retrying with a delay. (This was specific to the old `@bind-Value` text-input forms; the Photo/Document forms are `InputFile`-based as of the 2026-08-17 upload rework and don't have this issue — Playwright's file-upload action doesn't race a SignalR round-trip the same way.)
  - **`IBrowserFile.OpenReadStream()` has a default 512KB read limit and throws if the file is bigger** — always pass the real cap explicitly (`OpenReadStream(maxAllowedSize: DocumentUpload.MaxPhotoBytes)` / `MaxDocumentBytes`), and validate the file (extension/content-type/size) via `DocumentUpload.Validate(...)` *before* opening the stream, not after — that's what actually turns an oversized upload into a clean user-facing error instead of an unhandled exception from `OpenReadStream` itself.
  - **A `<InputFile>`'s displayed filename is native browser element state that Blazor doesn't own — mutating your C# fields after a successful upload doesn't clear the picker.** `EquipmentDetail.razor`'s Photo/Document sections work around this by changing the `InputFile`'s `@key` (a `Guid` field bumped to `Guid.NewGuid()` after every successful save/cancel) — a `@key` change makes Blazor treat it as a new element and recreate it, resetting the native file input. Forgetting this leaves the picker showing the old filename after a successful upload, which reads as "did that actually save?" even though it did.
  - **`DocumentCatalog.IsPhotoLabel(...)` (or any other plain C# static method) can't appear inside a `db.Documents.Where(...)` LINQ expression** — EF Core's query translator throws `InvalidOperationException: ... could not be translated` at runtime (not compile time) because there's no SQL equivalent for an arbitrary .NET method call. `SetPhotoUploadAsync` already does this correctly (`.Where(d => d.EquipmentId == equipmentId).ToListAsync()` first, *then* `.FirstOrDefault(d => IsPhotoLabel(d.Label))` on the in-memory list) — copy that shape, don't inline `IsPhotoLabel` into the DB-side predicate. Hit this writing `DocumentUploadTests.Replacing_the_photo_overwrites_the_existing_row_instead_of_adding_a_second_one`; fixed by inserting `.AsEnumerable()` between the DB-side `Where` and the `IsPhotoLabel` filter.

**Auth split**: authentication (proving who you are — real Google OAuth, wired in `Program.cs` via `AddGoogle`) is separate from authorization (what you can do — `RequireRoleFilter` / `UserAuthorization.RequireRole` looking up the authenticated email's `Role` and `IsActive` in the `Users` table). Only authorization is covered by automated tests: real Google OAuth needs a live browser and a real account, so it can't run in CI. Tests authenticate via `TestAuthHandler`, a scheme registered only in `ApiFactory` that reads an `X-Test-Email` header. Use `factory.CreateClientAs("Operator")` (or `"Admin"` / `"Reader"`) in a test to get an `HttpClient` that's already seeded a User and attached that header — don't hand-roll authenticated requests. `TestAuthHandler` only exists in the test factory; it is not available against a real `dotnet run` process, so live/browser verification of authorized routes needs an actual signed-in Google session (or a page-context `fetch()` from Playwright against an already-signed-in browser tab), not the test header.

`Equipment.Status` is an `EquipmentStatus` enum, not a string — stored as text (`HasConversion<string>()` in `AppDbContext`) and serialized as text (`JsonStringEnumConverter` in `Program.cs`), so the wire format reads `"Active"`/`"Retired"` even though the type is safe internally.

**`BusinessTime` (`src/QrSimple.Api/BusinessTime.cs`) is the app's first timezone-aware code**, added for inspection records (`docs/plans/0002-inspection-records.md` decision 24). The server runs in Fly's `ord` region (Chicago); users are in Mongolia (UTC+8) — a 13-14 hour gap. Anything that means "today" from a Mongolian operator's point of view (the inspection-upload form's date default, the 6-month recent/older split on the public inspections page) must go through `BusinessTime.Today()`/`.ToBusiness(...)`, never `DateTime.UtcNow`/`DateTime.Today` directly — with UTC, the upload form would default to yesterday's date and the 6-month boundary would shift by a day for roughly the first 8 hours of every Mongolian working day. It's a single hardcoded `Asia/Ulaanbaatar` constant, not per-Organization config, deliberately (see the class's own comment for why). Verified present in both the production runtime image (`mcr.microsoft.com/dotnet/aspnet:10.0`) and the devcontainer as of 2026-08-29 — `TimeZoneInfo.FindSystemTimeZoneById` resolves in both; if it ever throws `TimeZoneNotFoundException`, suspect a base-image change dropping `tzdata`, not the app code.

**Database schema**: the app uses real EF Core migrations (`Database.Migrate()` in `Program.cs`), not `EnsureCreated()`. Adding/changing a model requires a new migration (`dotnet dotnet-ef migrations add <Name> ...`, see [docs/database-migrations.md](docs/database-migrations.md)) — model changes with no matching migration will not apply to any real database (Testcontainers gets a fresh DB every run so this is easy to miss locally). That doc also covers the one-time bootstrap step for any pre-existing database that was created via the old `EnsureCreated()` path (already done for the shared local dev DB as of 2026-08-14 — no need to repeat it there).

## Running tests

**Preferred: the devcontainer** (`.devcontainer/devcontainer.json`). VS Code on this machine is a Flatpak, which sandboxes it enough to cause two separate classes of pain: the `.NET Install Tool` extension misdetects the distro (it reads `/etc/os-release` from inside the Flatpak runtime, not the real host), and env vars set via `~/.bashrc` don't reliably reach it (GUI-launched Flatpak apps don't source login-shell profiles). The devcontainer sidesteps both — .NET ships baked into the image, and every env var it needs is set in `devcontainer.json` itself, not inherited from a shell. Open the folder in VS Code → "Reopen in Container." Every `runArgs`/`mounts`/`postCreateCommand` entry in that file has a comment explaining *why* — this took real trial and error (SELinux relabeling breaking host socket access, rootless podman's UID remapping, sibling-container port reachability, a missing `libfontconfig1` in the base image) to get to 22/22 passing; read the comments before changing any of it.

**Fallback: bare host shell** (if you're not using the devcontainer, e.g. running from a real terminal rather than VS Code):

```bash
export DOTNET_ROOT="$HOME/.dotnet"; export PATH="$DOTNET_ROOT:$PATH"
export DOCKER_HOST="unix://$XDG_RUNTIME_DIR/podman/podman.sock"
export TESTCONTAINERS_RYUK_DISABLED=true
dotnet test
```

These three env vars are also appended to `~/.bashrc`, but non-interactive shells (including how the Bash tool invokes commands, and how Flatpak VS Code launches) don't reliably source it — export them explicitly per command rather than assuming they're already set. A `.runsettings` file also injects them for VSTest specifically (`dotnet test --settings .runsettings`), which is what lets VS Code's Test Explorer work even outside the devcontainer.

## Live browser testing

Before diagnosing missing browser tools, Chrome/CDP, ports 8931/9222/5078, or an empty `[]` response, read [docs/local-browser-testing.md](docs/local-browser-testing.md). It is the durable restart and troubleshooting runbook for this Fedora + Flatpak VS Code + devcontainer setup.

Important facts for every new agent:

- Codex and Claude Code are interchangeable in this devcontainer: both read the same two HTTP MCP servers (`http://127.0.0.1:8931/mcp` Playwright, `http://127.0.0.1:8932/mcp` project MCP), Codex via `.codex/config.toml`, Claude via `.mcp.json` at the repo root. Either agent can pick up a task the other started without re-registering anything. Do not replace either config with a `/var/home/...` stdio launcher; that host path is inaccessible from inside the devcontainer.
- The devcontainer uses host networking, so either agent can reach the Fedora-hosted Playwright MCP service, Chrome CDP on port 9222, PostgreSQL on port 5432, and the API on port 5078 through `127.0.0.1`.
- After a PC restart, the user runs `./scripts/start-chrome-for-playwright.sh` once in a **Fedora host terminal**. It starts the existing `qr-simple-db`, starts/replaces the Playwright MCP service, and opens disposable-profile Chrome.
- The API itself is started in the **devcontainer terminal** with `dotnet run --project src/QrSimple.Api --launch-profile http`.
- That `http` profile (port 5078 only) is enough for the plain API and public scan page, but **not** for testing real Google sign-in / the admin UI end to end: the OAuth `redirect_uri` is hardcoded to `https://localhost:7040/signin-google` (Cloud Console + `scripts/setup-google-oauth.sh`), so sign-in only works with `--launch-profile https` (binds 7040 + 5078). If port 7040 is already occupied — VS Code's automatic port-forwarding is a known culprit — the OAuth callback fails with `AuthenticationFailureException: The oauth state was missing or invalid`; free it via VS Code's Ports panel ("Stop Forwarding Port"), don't `kill` the forwarder.
- A browser response of `[]` at `/categories` is a successful empty API response, not a broken UI. This project is primarily an API; the rendered public page is `/e/{equipment-id}` after Equipment exists.
- Do not rebuild the devcontainer merely because browser tools are missing. Check the runbook's readiness commands and restart only the Codex extension/new agent after the MCP service is available.
- `docs/local-browser-testing.md`'s "Testing real Google sign-in" section also covers: `TestAuthHandler`'s `X-Test-Email` header only exists in the test factory, not a live `dotnet run` process (use a real signed-in session, or a Playwright page-context `fetch()`, for live authorized-route checks); why a page that still looks "signed in" right after clicking Sign out is not proof sign-out failed (Google's silent SSO re-auth); and the discrete-steps restart procedure for a backgrounded `dotnet run` (no hot reload — a single chained kill-and-restart command is prone to silently failing).

## Project-local MCP for the devcontainer agent

If you are starting a fresh Codex or Claude Code agent for normal `qr-simple` development, first read [docs/local-agent-mcp.md](docs/local-agent-mcp.md). It documents the project-local read-only MCP that lives inside the devcontainer and gives the agent stable workspace/app inspection tools.

Important facts:

- Start it from a **devcontainer terminal** with `./scripts/start-qr-simple-mcp.sh`.
- It listens on `http://127.0.0.1:8932/mcp` and is registered in both `.codex/config.toml` and `.mcp.json`.
- It is read-only by design. Keep browser automation in the separate Playwright MCP.
- The first tools are `workspace_search`, `workspace_read`, `app_health`, `route_inventory`, `route_auth_summary`, and `latest_test_failures`.
- After a PC or VS Code restart, start the MCP again before launching a new agent, Codex or Claude.

### Environment gotchas

This machine is Fedora Silverblue (immutable OS) with no Docker and no `dotnet` preinstalled, and VS Code is a Flatpak. None of this is a config-file fact you'd find by looking — worth knowing before you go hunting:

- **`dotnet`** is a user-local install at `~/.dotnet` (via the official `dotnet-install.sh` script), not `rpm-ostree layer` — that would need a reboot. If `dotnet` is ever genuinely missing, reinstall the same way rather than reaching for the package manager.
- **No Docker daemon** — Testcontainers talks to `podman` instead via `DOCKER_HOST` pointed at the rootless podman socket (`systemctl --user enable --now podman.socket` if it's ever not running — check with `systemctl --user status podman.socket`). `TESTCONTAINERS_RYUK_DISABLED=true` is required because Ryuk (Testcontainers' resource-reaper sidecar) doesn't play well with rootless podman.
- **SkiaSharp native library version must match the managed package exactly.** `SkiaSharp.NativeAssets.Linux` is pinned to `3.119.1` in both `.csproj` files to match the `SkiaSharp` version ZXing.Net.Bindings.SkiaSharp pulls in transitively. If you bump either package and see `System.TypeInitializationException` / "native libSkiaSharp library... is incompatible" at test runtime (not compile time), the pin has drifted — check `dotnet build` restore logs for the actual resolved `SkiaSharp` version and re-pin `SkiaSharp.NativeAssets.Linux` to match.
- **VS Code's sandbox can't run host binaries directly** even though it has `filesystems=host` permission — `/usr/bin/podman` fails with a missing shared library when exec'd through the sandbox's bind-mounted view of it. `scripts/podman-for-vscode.sh` (used as `dev.containers.dockerPath`, set at **User** settings level — workspace-level wasn't picked up in time for the extension's own Docker-detection check) routes through `flatpak-spawn --host` instead, which actually executes on the host. If Dev Containers builds ever start failing with "podman: command not found" or a linker error, check that setting first.
- **`updateRemoteUserUID` must stay `false`** (set in `devcontainer.json`). The CLI's version of that feature generates a temp Dockerfile inside the Flatpak sandbox's own private `/tmp`, then hands the path to a command that actually runs on the host via `flatpak-spawn --host` — the host process can't see a file the sandbox wrote to its own `/tmp` (same path string, two different filesystems), so it fails with "the specified Dockerfile does not exist." `--userns=keep-id` in `runArgs` already does the same UID-matching job correctly, so this feature is redundant here, not just broken — don't re-enable it looking for a "better" fix.
- **A prior agent working outside the devcontainer (directly on the Fedora host, apparently as root) can leave `obj`/`bin` root-owned.** This surfaces inside the devcontainer as `dotnet build`/`dotnet test` failing with `MSB3491: Access to the path '.../obj/Debug/net10.0/....cache' is denied`. Diagnose with `find <repo> -user root`; fix with `sudo rm -rf` on the affected `obj`/`bin` directories (pure build artifacts, always regenerable/safe to delete) and `sudo chown -R vscode:vscode` on any tracked source files it also touched (e.g. `Migrations/*.cs`) — passwordless `sudo` is available in this devcontainer for exactly this.
- **The host's inotify instance ceiling (128) is shared across every process on the machine** — VS Code, Codex, podman, and anything else watching files all draw from the same pool. A full `dotnet test` run can hit it and produce failures that look like real regressions but aren't; a serial/scoped run of just the affected test classes passing is the tell. Raising the limit (`fs.inotify.max_user_instances`) needs a host-level `sysctl` change, not something fixable from inside the devcontainer — if you see flaky/inconsistent `dotnet test` failures that don't reproduce when run narrower, suspect this before the code.

## Deployment

Live on Fly.io as of 2026-08-17 (app `qr-simple`, see `fly.toml`) — deploys have been running successfully on every push to `main` since then; this doc previously said "not deployed anywhere yet as of 2026-08-16," which had gone stale. Pipeline: a multi-stage `Dockerfile` (repo root, builds only `src/QrSimple.Api` — `QrSimple.Mcp` is a devcontainer-only dev tool and is never packaged) and `.github/workflows/ci-cd.yml` (a `test` job on every push/PR, a `deploy` job on push to `main` gated on `test` passing, targeting Fly.io via `flyctl deploy`). As of 2026-08-29 both triggers carry a `paths-ignore: ["**.md", "docs/**"]` filter, so a docs/markdown-only push or PR skips CI and the redeploy entirely — don't expect a test run or a new Fly release from a docs-only commit, and don't add non-doc files under a path this filter would exclude. `fly.toml` pins `auto_stop_machines = 'off'` / `min_machines_running = 1` deliberately — Blazor Server's per-session SignalR circuit doesn't survive scale-to-zero, so a normal Fly idle-scale-down would silently break navigation for whoever's mid-session. `Program.cs` calls `app.UseForwardedHeaders(...)` (before `UseHttpsRedirection()`, with `KnownNetworks`/`KnownProxies` cleared) so it works correctly behind a TLS-terminating edge proxy like Fly's — without it, a platform that forwards plain HTTP to the container both redirect-loops and makes Google's OAuth challenge build an `http://` `redirect_uri` that never matches the `https://` one registered in Google Cloud Console.

**Docker/CI static-asset gotcha (real, reproduced, not a cache artifact):** `QrSimple.Api.csproj` explicitly references `Microsoft.AspNetCore.App.Internal.Assets` (pinned to match the other net10.0 packages). Without it, a clean/fresh `dotnet publish` (any environment with an empty NuGet cache — Docker, CI runners) silently produces an empty `staticwebassets.endpoints.json` and no `wwwroot/_framework` folder at all: the app still builds and boots fine, but `_framework/blazor.web.js` 404s and every interactive Blazor nav click breaks post-deploy, while `dotnet run` from source still looks fine locally (masking the bug in normal dev). `Program.cs` uses `app.MapStaticAssets()` (not `UseStaticFiles()`) to serve from that manifest, per current .NET 9+/10 guidance. Confirmed via direct clean `--no-cache` Docker builds with matching SDK versions — this is a genuine implicit-package-resolution gap for this project's environment, not something explained by SDK version alone. If `_framework/blazor.web.js` ever 404s again in a deployed environment, check this package reference and the `MapStaticAssets()` call before anything else. The Fly.io app/Postgres/secrets were set up, and the prod redirect URI added in Google Cloud Console, as a one-time manual step by the project owner (needed real account access) around 2026-08-16/17 — see chat history from then for the step-by-step if the same needs redoing (e.g. a new environment, or credentials rotated). `PublicBaseUrl` (set per-environment today via `appsettings.Development.json`/`appsettings.json`, would need a `PublicBaseUrl` secret on any real deploy target) is baked into every generated QR code's URL, so getting it wrong on a real deploy silently prints QR codes that point at the wrong host.

**The HTTPS dev certificate is *not* persisted across rebuilds** (`dotnet dev-certs https`, unlike the user-secrets store above, isn't mounted from the host). `devcontainer.json`'s `postCreateCommand` runs `dotnet dev-certs https --trust` on every container creation to regenerate and trust it automatically (harmless no-op if a cert already exists) — without this, the `https` launch profile fails outright with "No server certificate was specified" until someone runs that command by hand, which silently blocks local Google sign-in testing (the OAuth redirect_uri is registered against `localhost:7040`, HTTPS-only).
